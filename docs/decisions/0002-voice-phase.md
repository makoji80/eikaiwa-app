# 0002. 音声フェーズ（録音・文字起こし・読み上げ）の実装方針

- 日付: 2026-09-25
- 状態: 採用（押して話す方式のみ。連続対話・割り込みは未実装で次フェーズ以降の課題）

## 背景

仕様書 v2.0 セクション5・9に基づき、Phase 1の次段階として音声入出力を実装する。ユーザー指示により対象は「日本語・英語の録音／文字起こし」「転記の確認・編集」「AI応答の読み上げ」「再録音」「マイク拒否時のテキスト切替」。押して話す方式のみで良いとされている。録音データは保存方針が決まるまで永続保存しない。

## 決定

1. **音声データは一切永続化しない。** `/api/transcribe` はbase64音声をメモリ上でデコードしAIプロバイダに渡した後、破棄する。ディスクにもDBにも書き込まない。`SpeechAsset` テーブルはこのフェーズでも未使用のまま（Phase 5以降、保存方針が決まった場合に配線する）。冪等性テーブルにはリクエストボディのSHA256ハッシュのみを保持し、音声本体は保持しない。
2. **読み上げ(TTS)は端末上で行う（`expo-speech`）。** サーバー往復・音声ファイルの生成/送受信/保存が一切発生しないため、(1)の「保存しない」要件を構造的に満たす。仕様書セクション8の `synthesize` API契約は定義のみ残し、このフェーズでは配線しない（将来、高品質な音声が必要になった場合にサーバーサイドTTSへ切り替える余地を残す）。
3. **音声アップロードは `audio_base64` 直送。** オブジェクトストレージが未導入のため、仕様書の「upload_ref」経路は実装しない。短い発話単位（押して話す）が前提のため、JSON内base64で十分と判断。この経路専用に `/api/transcribe` ルートのみボディサイズ上限を拡張(15MB)し、他ルートは小さいままにした。
4. **押して話す方式のみ。** 連続音声認識・割り込み（話し始めたらAI音声を止める）は未実装。仕様書5.の「実装基盤が同時会話を安全に扱えない段階では、押して話す方式で先に出す」に対応する暫定実装。
5. **音声はテキストフローに合流させる。** 録音→文字起こし結果は既存の「JP意図入力欄」または「英語入力欄」にそのまま反映されるだけで、compose/replyのAPI・DB書き込みロジックは一切変更していない。「AI提案文」と「本人が実際に発話した文」の区別は、本人が転記を確認・編集して明示的に送信ボタンを押した時点で初めて `TranslationAttempt.user_spoke=true` になる既存の仕組みがそのまま機能する。
6. **STT/TTSの言語判定は簡易固定。** 日本語意図の録音は `locale=ja-JP`、英語発話の録音は `locale=en-US` を固定で送る（本人のレベル・話者適応は行わない）。
7. **短すぎる録音の検知はバイトサイズの閾値のみ。** 実際の音声長・無音区間解析は行わず、base64デコード後のバイト数が2000バイト未満なら422 `audio_too_short` を返す簡易ヒューリスティック。

## 既知のギャップ（次フェーズ以降の課題）

- 割り込み（バージイン）・連続対話は未実装。
- 無音検出・タイムアウトは簡易的（サイズ閾値のみ）。
- 通話/バックグラウンド移行時の録音の適切な停止・再開は未検証（実機でのみ確認可能、下記チェックリスト参照）。
- OpenAI Whisper連携（`OpenAiProvider.transcribe`）は実鍵での動作検証ができていない。
- STTの精度・レイテンシは計測していない（Mockプロバイダは固定文字列を返すのみ）。
